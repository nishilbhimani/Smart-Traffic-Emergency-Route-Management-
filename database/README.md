## 🚀 How to Initialize, Run & Test the Database

### Step 1: Initialize the Database (1-Step Automatic Setup)
Run the initialization script from the project root directory:

```bash
python3 database/init_db.py
```

**What this command does:**
1. Creates a clean SQLite database file at [`pulse.db`](pulse.db).
2. Executes [`schema.sql`](schema.sql) to build all 9 tables, primary keys, foreign keys, and indexes.
3. Executes [`seed.sql`](seed.sql) to populate realistic Mumbai emergency transit records.
4. Executes and registers all analytical views (`vw_active_dispatches`, `vw_signal_realtime_status`, `vw_fleet_readiness`, `vw_corridor_efficiency`).
5. Performs an automated integrity check and outputs row counts and active missions directly to your terminal.

## 🏗️ Database Schema Summary (9 Core Tables)

1. **`vehicles`**: Emergency fleet units (Ambulance, Fire Tender, Police Interceptor, Bike Medic) with speed, driver, equipment, status, and live coordinates.
2. **`traffic_signals`**: The 6 Mumbai intersections (Bandra Kalanagar, Mahim Causeway, Dadar TT, Worli Sea Face, Haji Ali, Byculla) with preemption state, cycle duration, and override mode.
3. **`incidents`**: Emergency alerts requiring rapid response, priority level (`CRITICAL`, `HIGH`, `MEDIUM`), location, and resolution timestamps.
4. **`routes`**: Pre-calculated transit corridors (distance in km, baseline travel time, and typical congestion).
5. **`route_signals`**: Many-to-Many junction table mapping which traffic signals are encountered on each corridor in sequential order.
6. **`dispatch_missions`**: Connects vehicle, incident, and corridor into an active mission with live ETA and delay saved.
7. **`preemption_logs`**: Safety audit log tracking each green-wave preemption event (request time, grant time, release time, clearance speed).
8. **`vehicle_telemetry`**: High-frequency breadcrumb data recording instantaneous speed, progress percentage, and voice instructions.
9. **`performance_metrics`**: Daily aggregated KPIs comparing baseline vs. preemption response times.

## 🔌 Instructions for the Backend Developer

If you are developing the Node.js / Express or Python / FastAPI backend, here is how you connect:

### Option A: Using SQLite (`pulse.db`) — Recommended for Local Dev
No database server installation required.

**Node.js (Better-SQLite3 or SQLite3):**
```javascript
const Database = require('better-sqlite3');
const path = require('path');

const db = new Database(path.join(__dirname, '../database/pulse.db'), { verbose: console.log });

// Example: Fetch active missions
const activeMissions = db.prepare('SELECT * FROM vw_active_dispatches').all();
console.log(activeMissions);

// Example: Trigger signal preemption
const triggerPreemption = db.transaction((missionId, vehicleId, signalId) => {
  db.prepare(`
    INSERT INTO preemption_logs (mission_id, vehicle_id, signal_id, requested_at, granted_at, trigger_type, status)
    VALUES (?, ?, ?, CURRENT_TIMESTAMP, CURRENT_TIMESTAMP, 'PROXIMITY_AUTO', 'GRANTED')
  `).run(missionId, vehicleId, signalId);

  db.prepare(`
    UPDATE traffic_signals 
    SET current_state = 'PREEMPTED', is_preempted = 1, preempted_by_vehicle_id = ?, updated_at = CURRENT_TIMESTAMP
    WHERE id = ?
  `).run(vehicleId, signalId);
});
```

**Python (FastAPI / Flask):**
```python
import sqlite3

def get_db_connection():
    conn = sqlite3.connect('database/pulse.db')
    conn.row_factory = sqlite3.Row
    return conn

@app.get("/api/v1/signals")
def get_signals():
    conn = get_db_connection()
    signals = conn.execute("SELECT * FROM vw_signal_realtime_status").fetchall()
    conn.close()
    return [dict(s) for s in signals]
```

## 📊 Relational DBMS Architecture Highlights

Key architectural concepts and design patterns:
1. **Normalization:** The database is in **3NF (Third Normal Form)**. Multi-valued dependencies are eliminated via the `route_signals` junction table, and transitive dependencies are eliminated by separating `traffic_signals` from `preemption_logs`.
2. **Referential Integrity:** Primary and foreign keys are explicitly enforced using `ON DELETE CASCADE` and `ON DELETE SET NULL`.
3. **Indexing Strategy:** B-tree indexes are created on frequently queried columns (`status`, `vehicle_id`, `signal_id`, and `corridor_name`) to ensure sub-millisecond query execution.
4. **Views for Abstraction:** Views (`vw_active_dispatches`, `vw_signal_realtime_status`) abstract complex multi-table joins away from the presentation and API layer.
